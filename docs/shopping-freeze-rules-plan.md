## סטטוס מימוש (14.10.2026)

**החלטות שנקבעו:** (1) אחרי ההקפאה עובד רגיל לא יכול לעשות כלום ברשימה: לא להוסיף, לא לערוך, לא למחוק ולא לסמן "נרכש". (2) הגדרת קציבה חדשה לא נוגעת בהקפאה שכבר חלה, והיא חלה על הסבב הבא. (3) הכללים נפרסים אוטומטית ב-GitHub Actions. (4) תור בקשות המוצרים לא משתנה.

**מה מומש, ובמה זה שונה מהתוכנית שלמטה** (הסעיפים 3.2 עד 3.4 נשארו כתיאור התוכנית המקורית):
- `src/app/shopping/lib/freeze.ts`: חישוב המועד באזור הזמן של ישראל (עם מעבר שעון קיץ), משותף ללקוח ולשרת. `getCutoffStatus` משתמש בו, כך שהמסך והכללים מסכימים. 9 בדיקות יחידה: `npm run test:unit`.
- **נתיב הסנכרון הוא הכותב היחיד של `freezeAt`.** במקום שהלקוח של המנהל יכתוב אותו בשמירת הגדרות ובסגירה, `POST /api/shopping/sync-freeze` מחשב אותו מהמצב האמיתי (הגדרת הקציבה והפריטים הקיימים) ומחזיר אותו לאותו ערך. כל לקוח פתוח מחשב לבד מה הערך הצפוי, ואם הוא שונה ממה ששמור, קורא לנתיב (לא יותר מפעם ב-15 שניות). לכן אין צורך בקריאות מפורשות אחרי שמירת הגדרות או סגירת רשימה, והמצב התקוע של שבוע בלי הזמנות נפתר בלי מנהל.
- בהוספה שנדחתה עם `permission-denied` נקרא הנתיב פעם אחת ומנסים שוב, ואם עדיין נדחה מוצגת "הרשימה הוקפאה לאחר מועד הקציבה ולא ניתן לשנות אותה". אותה הודעה מוצגת בעריכה, שינוי כמות והעברה בין רשימות.
- `firestore.rules`: כלל הוספה ועדכון שמחזיקים בהקפאה (`isShoppingListFrozen`). הוסרו כללי `archived`.
- `tests/firestore.rules.test.ts`: 21 בדיקות מול אמולטור Firestore (`npm run test:rules`, דורש Java).
- `.github/workflows/firestore-rules.yml`: בדיקות על כל שינוי רלוונטי, ופריסת הכללים בעת מיזוג ל-`main`.

**ממצא שלא היה בתוכנית, ותוקן:** ב-`firestore.rules` הפונקציות `hasRole`, `isManager`, `isStaff` ו-`isShoppingManager` הריצו מחדש את `getUserData()` ושרשרת ארוכה של השוואות לכל תפקיד. באמולטור, אפילו עם הכללים המקוריים (לפני כל שינוי שלי), הוספה או עדכון של פריט ע"י עובד רגיל (לא מנהל או לוגיסטיקה) נכשלו עם "maximum of 1000 expressions to evaluate has been reached". כתבתי מחדש את ארבע הפונקציות כך ש-`userRoles()` נקראת פעם אחת לכל קריאה, בלי לשנות מי נחשב לאיזה תפקיד, והוספתי בדיקות שמוכיחות שזה נשאר כך (תפקיד בשדה `role` בלבד, במערך `roles` בלבד, משתמש בלי מסמך, משתמש שאינו עובד, ועקיפת מנהל מערכת). **לא ידוע אם גם בייצור עובדים רגילים נחסמו, וכדאי לבדוק זאת אחרי הפריסה.**

**מה נדרש ממך לפני שהפריסה האוטומטית תעבוד** (פעם אחת, בהגדרות המאגר ב-GitHub):
1. סוד `FIREBASE_SERVICE_ACCOUNT`: מפתח JSON של חשבון שירות עם התפקיד "Firebase Rules Admin" (ו-"Service Usage Consumer").
2. משתנה `FIREBASE_PROJECT_ID`: מזהה פרויקט ה-Firebase.
בלי שניהם, עבודת הבדיקות תרוץ אבל שלב הפריסה ייכשל. עד אז אפשר לפרוס ידנית עם `firebase deploy --only firestore:rules`.

## 1. הבעיה

אחרי מועד הקציבה הרשימה "מוקפאת", אבל **רק בממשק**: `isListFrozen` ב-`useShoppingData.ts` ו-`isUserBlockedByFreeze` ב-`AddProductOverlay.tsx:73`. בכללי Firestore (`firestore.rules`, בלוק `shopping_requests`) אין שום תנאי זמן, ולכן:
- כל עובד (`isStaff`) יכול להוסיף פריט אחרי המועד, ישירות מול ה-API, או סתם מטאב ישן שנפתח לפני המועד.
- כל עובד יכול לשנות אחרי המועד שם, כמות, הערות, קטגוריה ורשימה של פריט קיים (`updateItem`, `updateQuantity`, העברה בין רשימות).
- הרשימה יכולה להשתנות אחרי שכבר שלחו אותה לספק או הדפיסו אותה.

**מי לא נחסם (בכוונה):** מנהלים ולוגיסטיקה (`isShoppingManager`), כמו בממשק היום. זה נדרש גם ל"מוצרי דקה ה-90" במסך הסגירה. מנהל מערכת (`isAdmin`) לא נחסם בכל מקרה, כי יש `match /{document=**}` שנותן לו גישה מלאה לכל דבר.

## 2. למה זה לא פשוט

הכללים לא יכולים לבצע שאילתות. "הרשימה מוקפאת" מוגדרת היום בצד הלקוח כך:

> מועד הקציבה האחרון חלף **וגם** יש ברשימה פריט שנוצר לפני אותו מועד (כלומר לא נסגרה).

שני חלקים ממנה אי אפשר לחשב בכללים:
1. **"יש פריט שנוצר לפני המועד"** דורש לספור פריטים. הכללים רואים רק את המסמך שנכתב ומסמכים שמצביעים עליהם בנתיב מפורש (`get()`).
2. **חישוב "המועד האחרון שחלף"** מ-`cutoffConfig` (יום בשבוע ושעה) דורש אזור זמן. בכללים `request.time` הוא UTC בלבד, וישראל עוברת בין UTC+2 ל-UTC+3. חישוב כזה בכללים שביר.

לכן הכללים צריכים **מצב שמור**: מסמך שאומר מתי הרשימה מוקפאת, ושמישהו אחר מתחזק.

## 3. הפתרון המוצע

### 3.1 מודל נתונים
בשדה חדש במסמך `settings/shopping` (לכתיבה שם כבר מורשים רק מנהלים ולוגיסטיקה, ולכן עובד רגיל לא יכול להזיז את הנעילה):

```
freezeAt: {
  supermarket: Timestamp | null,   // הרגע שבו הסבב הנוכחי של רשימת הסופר מוקפא
  large:       Timestamp | null,   // כנ"ל לרכש גדול
}
```

- `null` או שדה חסר = לא מוקפא (גם כשהקציבה כבויה). כך הפריסה הראשונית בטוחה ולא חוסמת כלום.
- `freezeAt` שכבר חלף = הרשימה מוקפאת עד שמישהו סוגר אותה.
- כל רשימה בנפרד, כמו היום (סגירת הסופר לא נוגעת ברכש).

### 3.2 כללים (טיוטה)

```
// הרגע שבו הרשימה הזו הוקפאה (או null אם לא מוקפאת).
function freezeAtFor(listType) {
  let path = /databases/$(database)/documents/settings/shopping;
  return exists(path)
    ? get(path).data.get('freezeAt', {}).get(listType == 'large' ? 'large' : 'supermarket', null)
    : null;
}

function isListFrozen(listType) {
  let at = freezeAtFor(listType);
  return at != null && request.time >= at;
}

function changedKeys() { return request.resource.data.diff(resource.data).affectedKeys(); }

// פריטים ישנים בלי listType שייכים לסופר (כמו belongsToList בקוד).
function itemList(data) { return data.get('listType', 'supermarket') == 'large' ? 'large' : 'supermarket'; }

match /shopping_requests/{docId} {
  allow read: if isAuthenticated();

  allow create: if isShoppingManager() || (
    isStaff() &&
    request.resource.data.requestedBy == request.auth.uid &&
    request.resource.data.status == 'approved' &&
    !isListFrozen(itemList(request.resource.data))
  );

  allow update: if isShoppingManager() || (
    isStaff() &&
    request.resource.data.status in ['pending', 'approved', 'purchased', 'deleted'] &&
    !changedKeys().hasAny(['requestedBy', 'requestedByName', 'createdAt']) &&
    (
      // הרשימה של הפריט לא מוקפאת: עריכה חופשית. העברה לרשימה אחרת נחשבת כהוספה אליה,
      // ולכן אסורה אם הרשימה שאליה מעבירים מוקפאת.
      (
        !isListFrozen(itemList(resource.data)) &&
        (!changedKeys().hasAny(['listType']) || !isListFrozen(itemList(request.resource.data)))
      ) ||
      // הרשימה מוקפאת: עובד רגיל רק מסמן "נרכש" או מחזיר ל"ממתין"/"מאושר", בלי לגעת בתוכן.
      (
        resource.data.status in ['pending', 'approved', 'purchased'] &&
        request.resource.data.status in ['pending', 'approved', 'purchased'] &&
        !changedKeys().hasAny(['name', 'category', 'quantity', 'notes', 'priority', 'listType', 'targetFramework'])
      )
    )
  );

  allow delete: if isShoppingManager();
}
```

הערות על הטיוטה:
- העברת פריט בין רשימות נבדקת מול הרשימה שאליה מעבירים, רק כשהשדה `listType` השתנה, כדי שסימון "נרכש" ברשימה מוקפאת לא ייחסם.
- הרשאת סימון "נרכש" אחרי ההקפאה נשארת, כי הקנייה עצמה מתבצעת אחרי המועד. מחיקה רכה (`deleted`) אחרי ההקפאה חסומה לעובדים.
- ביטול כללי `archived` (`resource.data.status != 'archived'` ו-`archivedAt`/`archivedBy`): הם משויכים לסטטוס שאין שום קוד שכותב אותו. מומלץ להסיר אותם באותה פריסה.
- `get()` על `settings/shopping` נספר מול מגבלת הקריאות של בקשה, ונחשב בחיוב כקריאת מסמך אחת לכל כתיבה של עובד. זה זניח בנפח כאן.

### 3.3 מי מתחזק את `freezeAt` (בלי cron)

אין היום שום משימה מתוזמנת, ואין `vercel.json`. אפשר להסתדר בלי אחת:

| אירוע | מי כותב | ערך |
|---|---|---|
| נשמרת הגדרת קציבה (`saveCutoff`, `useShoppingActions.ts`) | לקוח המנהל | המועד הבא של כל רשימה שלא מוקפאת כרגע |
| נסגרת רשימה (`closeCycle`) | לקוח המנהל, אחרי המחיקה | המועד הבא אחרי עכשיו, לאותה רשימה |
| המועד חלף והרשימה ריקה (אין מה לסגור) | נתיב API חדש (בסעיף 3.4) | המועד הבא אחרי עכשיו |
| קציבה כבויה | לקוח המנהל | `null` לשתי הרשימות |

**למה צריך את השורה השלישית:** בלי היא נוצר מצב תקוע. אם בשבוע מסוים אף אחד לא הזמין כלום, `freezeAt` חולף, הרשימה ריקה ואין מה לסגור (הכפתור "סגור רשימה" מושבת כשאין פריטים), והעובדים נחסמים בלי שום דרך להמשיך. בצד הלקוח זה לא קורה, כי הרשימה הריקה פשוט נחשבת לא מוקפאת.

חישוב "המועד הבא": הפונקציה היום ב-`cutoffUtils.ts` עובדת לפי השעון המקומי של הדפדפן. לצורך הכתיבה צריך פונקציה נפרדת, `nextCutoffAfter(config, from)`, שמחזירה את המופע הבא של `config.day` + `config.time` **באזור הזמן `Asia/Jerusalem`** (דרך `Intl.DateTimeFormat` עם `timeZone`, כך שמעברי שעון קיץ לא שוברים אותה). כך הערך זהה בלי קשר למכשיר שכתב אותו.

### 3.4 נתיב API לגלגול קדימה
`POST /api/shopping/roll-freeze`, בקוד שרת עם Firebase Admin SDK (שעוקף כללים):
1. מאמת ID token של משתמש מחובר ואת התפקיד שלו (כל עובד, לא רק מנהל).
2. לכל רשימה: אם `freezeAt` חלף **ואין אף פריט פעיל** (`pending`/`approved`/`purchased`) ברשימה, כותב `freezeAt = nextCutoffAfter(config, now)`.
3. הפעולה אידמפוטנטית ולא מקבלת שום ערך מהלקוח. היא רק מזיזה את המועד קדימה למועד אמיתי הבא, כך שאי אפשר לנצל אותה כדי לפתוח רשימה שיש בה פריטים.

הלקוח קורא לה:
- בטעינת דף הקניות, כשהוא רואה `freezeAt` שחלף והרשימה ריקה.
- כשהוספה נכשלה עם `permission-denied`: קוראים לנתיב פעם אחת ומנסים שוב.

הערה: קוד אתחול Firebase Admin מועתק היום בשני מקומות (`lib/firebase/admin.ts` ו-`api/notify/route.ts`). הנתיב החדש יסתמך על `lib/firebase/admin.ts` בלבד.

חלופה שנשקלה: cron של Vercel. היא דורשת `vercel.json` וחבילה שמאפשרת תדירות שעתית (בחבילה החינמית רק פעם ביום), ועדיין לא פותרת פריט שנוסף בדקה האחרונה. נתיב לפי דרישה פשוט יותר.

## 4. שינויים בצד הלקוח

- `lib/cutoffUtils.ts`: פונקציה חדשה `nextCutoffAfter(config, from)` באזור זמן ישראל, עם בדיקות (יום ראשון, שעה 00:00, מעבר שעון קיץ).
- `useShoppingActions.ts`: `saveCutoff` ו-`closeCycle` (דרך הקריאה ב-`page.tsx`) כותבים `freezeAt`.
- `useShoppingActions.ts` (`addProduct`, `changeStatus`, `updateItem`, `updateQuantity`): לתפוס `permission-denied` ולהציג הודעה ברורה ("הרשימה הוקפאה ולא ניתן להוסיף או לערוך"), במקום "שגיאה, נסה שוב".
- `useShoppingData.ts`: להחזיר גם את `freezeAt`, ולקרוא ל-`roll-freeze` כשצריך (סעיף 3.4).
- כדאי שהממשק יסתמך גם על `freezeAt` כדי לא להציג כפתורים שהכללים יחסמו (למשל עריכת כמות אחרי ההקפאה לעובד רגיל). היום הוא מסתמך רק על הכלל בצד הלקוח.

## 5. סדר פריסה (חשוב: אסור להפוך אותו)

1. **קוד הלקוח והנתיב** נפרסים ל-Vercel (נפרס אוטומטית עם מיזוג). הם כבר כותבים `freezeAt`, אבל הכללים עוד לא קוראים אותו, ולכן שום דבר לא נחסם.
2. **מילוי ראשוני:** אחרי הפריסה, מנהל נכנס לדף הקניות והלקוח כותב `freezeAt` לשתי הרשימות (או סקריפט חד-פעמי). לבדוק ב-Firebase Console שהשדה קיים.
3. **פריסת הכללים:** `firebase deploy --only firestore:rules`. הקובץ `firebase.json` כבר מצביע על `firestore.rules`, אבל Vercel לא פורס כללים, ולכן זה צעד ידני (או workflow ב-GitHub Actions, אם רוצים אוטומציה).
4. **בדיקת עשן** (סעיף 7, בדיקות ידניות).
5. **החזרה אחורה:** פריסה מחדש של הגרסה הקודמת של `firestore.rules`. הנתונים לא נפגעים, כי `freezeAt` רק שדה נוסף.

## 6. סיכונים

| סיכון | התמודדות |
|---|---|
| נעילה שגויה חוסמת עובדים בשבוע רגיל | `freezeAt` חסר או `null` = פתוח. גלגול קדימה לרשימה ריקה. מנהל יכול תמיד להוסיף ולסגור. החזרה אחורה של הכללים בדקה |
| פער שעונים בין הדפדפן לשרת | הכללים משתמשים ב-`request.time` של השרת. הממשק עלול להראות "פתוח" כמה שניות אחרי שהכללים כבר חוסמים. ההודעה על `permission-denied` מכסה את זה |
| אי-התאמה בין "מוקפא" בממשק ל"מוקפא" בכללים (הממשק מחשב לפי פריטים, הכללים לפי `freezeAt`) | לאחד: הממשק יסתמך על `freezeAt` ועל אותה פונקציה. עד אז ייתכנו הבדלים קטנים סביב רשימה ריקה |
| `closeCycle` נכשל באמצע (פריטים נמחקו ו-`freezeAt` לא עודכן) | הרשימה ריקה וה-`freezeAt` ישן, ולכן `roll-freeze` מזיז אותו קדימה בכניסה הבאה |
| שינוי הגדרת קציבה באמצע שבוע, כשהרשימה כבר מוקפאת | `freezeAt` של רשימה מוקפאת לא משתנה. הגדרה חדשה חלה על הסבב הבא. להחליט אם זה רצוי (סעיף 8) |
